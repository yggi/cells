# Land a pull request

Agents don't merge (`AGENTS.md`): this skill runs only on the owner's word, after the `review` skill's review found nothing serious.
cells is a package, so nothing deploys: a merge reaches the frontends only through a tag, and the tag is the `release` skill's.
Do the steps in order and stop at the first that fails.

Lifted from yggi/cell-studio .claude/skills/land/SKILL.md @ 85175ce (itself lifted from yggi/jambot's), without its deploy and live check; the issue handling (step 5) is the family's, 2026-10-16 (yggi/music-commons#4).

The REST API does all of it (`gh api`; a session's proxy refuses GraphQL, so `gh pr merge` and `gh issue close` may fail).
Every comment posted from a session ends with a blank line, `---` and `_Generated by [Claude Code](https://claude.ai/code)_`.

1. **The pull request is ready.**
   It is out of draft (ready: nothing left open in it, `AGENTS.md`), and its *Verified* names its current head as the commit that passed the pre-push hook (`pre-push: verify passed, <n> tests; tree <tree> stamped`), with `npm run test:all` where it reaches the folder or the slow tests.
   It has no conflicts with `main` (`gh api repos/yggi/cells/pulls/<n> --jq .mergeable_state` is not `dirty`; otherwise `git merge origin/main` into it once, verified again), and CI on the head is green or blocked, never red.
   The generated pages are current on that head: `npm run reference` leaves `git status` clean (the same test is in verify, so a diff means the head wasn't verified: stop and say so). Nothing regenerates on `main` after the merge: agents don't push to it.
2. **The owner has approved.**
   In the prompt ("merge if you find nothing", and nothing was found), or as a yes to the review's summary.
   Otherwise stop and ask.
3. **Merge it by squash**, the pull request's title as the message, so `main` reads `Title (#n)`: `gh api -X PUT repos/yggi/cells/pulls/<n>/merge -f merge_method=squash -f commit_title="<title> (#<n>)"`.
   A merge commit only when a reader of `git log` needs the branch's steps (as the extraction's history, #2), and the pull request says why.
4. **Update `main`.**
   `git fetch origin main && git checkout main && git merge --ff-only origin/main`, in a clone whose tree is clean.
5. **Handle its issues.**
   1. **Closed as said:** every `Closes #n` in the merged pull request closed its issue (`gh api repos/yggi/cells/issues/<n> --jq .state`).
      One that didn't (a `Closes yggi/<repo>#n` in another repository, a typo) is closed by hand, with a comment naming the pull request: `gh api -X PATCH repos/yggi/<repo>/issues/<n> -f state=closed -f state_reason=completed`.
   2. **Ticked:** a `Part of #n` epic's checklist line for this pull request is ticked, `- [x] … (#<pr>)`, by rewriting the epic's body with that one line changed (`gh api -X PATCH repos/yggi/cells/issues/<n> -F body=@<file>`).
      An epic with no line for it gets one comment naming what landed.
   3. **Follow-ups filed:** each line of the pull request's *Not done / follow-ups* that names work becomes an issue, or is one already and is linked, in the repository where it belongs: a language question here, a workbench one in yggi/cell-studio, Jambot's in yggi/jambot, the wire's in yggi/webmidi, one across the family in yggi/music-commons.
      The issue states its bounds as numbers (the `task` template).
   4. **References right:** an issue or pull request in another repository that the merged pull request mentions by a bare number is written `yggi/<repo>#n`, in its body and its comments; a bare `#n` here always means cells' own.
6. **No deploy.**
   A change a frontend would notice waits under *Unreleased* in `CHANGELOG.md` until a release; tagging it now is the `release` skill, on the owner's word.
7. **Say so** in a comment on the pull request: the merge commit, the issues closed, the epic line ticked, and the follow-ups filed, each by its number.

If a step after the merge fails, the merge stands: fix forward on a new branch, and say on the pull request what is left.
