# Agents

The cells language as a package: a minimal music language where everything is a cell, on top of Strudel's mini-notation; text in, events out, with no host of its own. Its frontends are [Cell studio](https://github.com/yggi/cell-studio) (the workbench) and [Jambot](https://github.com/yggi/jambot) (the interactive, multi-user frontend), each consuming a tag of this repository. **Start with [docs/MEMORY.md](docs/MEMORY.md)**; [docs/INDEX.md](docs/INDEX.md) lists every page. **What to do next:** look first at the central roadmap epic, [#81](https://github.com/yggi/cells/issues/81) (its twin is [yggi/jambot#358](https://github.com/yggi/jambot/issues/358)). The family of music projects and its rules: [yggi/music-commons](https://github.com/yggi/music-commons).

## Tools

- `npm run verify`: everything a push needs: (in a checkout with no `node_modules` it runs `npm ci` first, `tools/install-first.mjs`) `check` (the purity gate and the full typecheck), `lint`, `format:check`, `knip`, and the quick tests; the typechecks, ESLint and Prettier keep caches in `.cache/` (ignored; delete it to run them cold), so a second run checks only what changed. A pre-push hook runs it (`.githooks/pre-push`; the first `npm run verify` in a clone points git at it, and so does the session-start hook: a `prepare` script would break a frontend's install, `tools/hooks.test.ts`) and blocks a push that fails, or one with an untracked file that verify would see and the commit lacks, keeping its whole output in the git directory (`cells-verify-failed.log`); a run that passes, by hand or in the hook, stamps its tree in the common git directory, which the clone's worktrees share (`tools/verified.sh`), so the push of that tree from any of them doesn't run it again, and the hook prints the count of tests that passed (kept with the stamp, for a tree it doesn't run again). Never bypass it with `--no-verify`.
- `npm run test:all`: the quick and the slow tests (the folder over whole pieces and the MIDI library: 162 s on four cores, 2026-10-17, and 323 s with other agents loading them). Run it when you touch `src/engine/fold/`, `midiimport`, or anything the slow tests read.
- `npm run examples`: rewrites `src/engine/examples.generated.ts` from `examples/*.md`; `npm run fragments`, `src/repository/seed.generated.ts` from `fragments/**/*.md`; a test fails when either is stale.
- `npm run reference`: rewrites `docs/language/reference.md` from the parser's tables and the index of forms in `README.md`; a test fails when either is stale. Run it with any change to a parser table, an attribute or a parameter, and commit the result: nothing regenerates on `main`.
- `npm run types`: rewrites `types/` (the declarations a frontend typechecks against, through the `types` condition of `exports`) from `src/`; a test fails when it is stale. Run it with any change to an exported signature.
- `npm run dist`: rewrites `dist/` (`src/` as JavaScript for Node, through the `default` condition of `exports`; bundlers keep the source through `module`); a test fails when it is stale. Run it with any change to `src/`, and commit the result.
- Skills (`.claude/skills/`): `release` (verify `main`, the changelog and version, the owner's tag, the frontends' pins moved), `review` (a pull request in its own worktree, verified, its claims re-run, one review), `pianoroll` (what a text plays as a picture, before and after a change), `land` (a pull request merged by squash on the owner's word, then its issues: closed, its epic ticked, its follow-ups filed; no deploy). `node --experimental-transform-types --import ./tools/node-ts.mjs` runs the source under Node.
- `npm run structure -- [--cells] <input>...`: a text's structure, decision 049's measure (each leaf a braid writes, one per attribute value, one per cell, over the normal form; names, labels and comments free), for a change that claims a piece more compact; an input is `example:<key>`, a `.md` piece or fragment, or a `.cells` text (`tools/structure.ts`, until #157 builds it into Shorten).
- One file while iterating: `npx vitest run src/engine/parser/parser.test.ts`.

## Rules

Enforced (a failing check says so):
- **Pure.** `src/` typechecks with no host types at all (`tsconfig.pure.json`: no DOM, no Node, no bundler); the host globals it may use are the three in `src/host.d.ts`. Nothing here imports a frontend.
- Docs' ```` ```cells ```` blocks compile, `docs/INDEX.md` lists every page, relative links resolve, every decision is in `docs/MEMORY.md`'s list.
- Every example compiles with no diagnostics, a title, tags from the vocabulary, and its card.
- The folder's ratchets: no fold taken is lost, a set's score doesn't grow by more than 1 % (`src/engine/fold/ratchet.*.json`).
- Prettier owns whitespace; ESLint has no errors; knip finds no unused files or dependencies.

Judgment (nothing checks these; you do):
- **The text is the single source of truth.** A change to what the language means changes how the frontends' pieces sound: say so, and keep the examples sounding the same (the event snapshots) unless the change is the point.
- **A release is a tag.** Frontends depend on `github:yggi/cells#vX.Y.Z`, never a branch, and read [CHANGELOG.md](CHANGELOG.md) before they move it: a change a frontend would notice adds a line under *Unreleased*, and one that breaks a piece names its migration there (Shorten writes migrations). That is a minor version before 1.0, and the frontends' issues say what to migrate.
- A decision with a rationale gets `docs/decisions/NNN-slug.md` (the next number after the highest here or in Cell studio's list) and a line in `docs/MEMORY.md`.
- Code lifted from a sibling says where from (`Lifted from yggi/<repo> <path> @ <commit>`).

## Working

- Work on the branch the session gives you; never push to `main`; **agents don't merge**. Open a pull request from the template (`Closes #n`, or `Part of #n` for one rung of an epic; what and why, the commit verified, follow-ups); a **draft** is whatever is not ready to be merged at any time: a proposal, with open work or undecided questions (it doesn't wait on the owner or on a review: those are not what makes a pull request a draft). A pull request out of draft is **ready**: expect it to be reviewed and merged, so open it that way only when nothing is left open. Setting a draft to ready ends the work on it: more work is a different pull request.
- **Just do, no comment:** typos, nits, a local rename, an added test, fixing a check you broke. **Do and say in the pull request:** a fix beside your change that it needs. **File an issue instead of widening it:** anything out of scope you notice. **Stop, push back, recommend:** anything that changes how a piece sounds or what it means (an event snapshot that moves, a form removed or respelled), a vector of the hub's contracts cells would stop meeting, a change to purity or to the source-of-truth rule, anything that could break a frontend at its next pin (its install, its typecheck), a scope far beyond the issue, anything irreversible or outward-facing (a tag). - An issue meant for an agent states each bound as a number (a size, a count, a time), or says "choose it and name it".
- A tool's module and its test live side by side in `tools/` (`tools/<name>.ts`, `tools/<name>.test.ts`); the language's tests sit beside its code in `src/`.
- **CI is a witness, not the gate:** the repository is public, so Actions costs nothing here (#242). The workflow runs `verify` and the slow tests, as two jobs, on every push to a pull request out of draft, nightly on `main`, and by hand (the release's first step). A draft runs nothing. The gate is still `npm run verify` before the push: a red CI on a ready pull request means the gate missed something. Say in the pull request which commit you verified.
